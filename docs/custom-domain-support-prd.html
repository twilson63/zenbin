ZenBin Custom Domains MVP

Status: planned

Definition

A custom domain is a globally unique, DNS-verified hostname that aliases one already-owned ZenBin subdomain. It changes request routing only: the subdomain signing key, page IDs, content, viewer authentication, and provenance remain authoritative. An active mapping requires both TXT ownership proof and a ready managed certificate provider result.

Goals

  • Signed, owner-only create/list/verify/update/delete endpoints under a claimed subdomain.
  • Strict hostname normalization and global uniqueness; no IPs, localhost, wildcards, public-suffix-only names, or ZenBin-owned hosts.
  • Random 256-bit TXT challenge, provider-neutral DNS/TLS interfaces, idempotent verification, actionable status/error codes.
  • Route only active custom hosts through the existing subdomain renderer; unknown external hosts are neutral 404s.
  • Deactivate before provider deletion; clean attached domains before deleting a subdomain; audit lifecycle actions.

Non-goals

  • Live Cloudflare/ACME integration, DNS polling/jobs/webhooks, multiple aliases, redirects, organization delegation, or customer-uploaded certificates.
  • Changing page ownership, weakening host-scoped viewer authentication, accepting forwarded host headers, or exposing provider credentials/raw token after activation.

Research evidence

Security constraints

  • Use direct Host only; normalize before lookup; never derive a storage key from raw host.
  • Route exclusively active records. DNS and certificate readiness both gate activation.
  • All mutations inherit existing Ed25519 signature + nonce protections and additionally check subdomain ownership.
  • Provider diagnostics are sanitized; no TLS keys/provider credentials are persisted.

Judge rubric / definition of done

Every plan criterion has passing evidence; no inactive or foreign host can serve tenant content; the API is compatible with existing signed request conventions; provider integration remains narrow and production-safe.
